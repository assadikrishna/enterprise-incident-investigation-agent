Capstone Checkpoint 3.1 
Enterprise Incident Investigation Agent 
RAG and Retrieval Design Integration

Decision: Is Retrieval Required?
Retrieval is required for the Enterprise Incident Investigation Agent because incident investigation often depends on knowledge beyond the LLM’s training data and the immediate incident context. The earlier agent could retrieve incident details, search application logs, and access a known service runbook directly through predefined tools. That worked when the relevant operational evidence or troubleshooting resource was known, but the design did not provide a semantic mechanism for discovering relevant information across a broader collection of runbooks and historical incident reports. The Module 3 design therefore adds semantic retrieval so the agent can use evidence gathered during the investigation to form focused queries and retrieve relevant knowledge based on conceptual similarity rather than requiring the correct document or exact keywords to be known in advance. Historical incidents are included because a current issue may resemble a prior investigation even when no runbook contains the specific resolution. Retrieval supports investigation by suggesting hypotheses; it does not automatically establish causation.

Semantic Retrieval Integration
The agent now includes a search_knowledge[] action. The synthetic knowledge base contains service runbooks and historical incident reports stored separately under the knowledge directory. A SemanticRetriever loads these documents and creates embeddings using a SentenceTransformer model. When the agent determines that knowledge search may help, it passes a natural-language query to search_knowledge[]. The retriever compares the query with stored document embeddings and returns the most relevant results, including the source and similarity score. The retrieved text is then supplied as a tool observation and becomes additional evidence for the next reasoning step. Logs remain a separate operational search tool because they are timestamped events, while runbooks and historical incidents are longer knowledge documents suited to semantic similarity search. Retrieval is invoked by the LLM during the Reason-Act-Observe loop rather than being forced after every step.

Demonstration That Retrieval Influences Agent Behavior
Test incident INC-001 involved HTTP 503 errors in payment-service after deployment of version 2.3. The log-search tool returned evidence of HTTP 503 responses, database connection-pool exhaustion, and database timeout or retry failure. The payment-service runbook recommended checking database connectivity, connection-pool utilization, and recent deployment changes. At that point, the evidence identified the immediate technical symptom but not the underlying cause.
The LLM then independently selected search_knowledge[], showing that semantic retrieval was not hard coded as the next action. Retrieval returned INC-101, a previous payment-service incident involving HTTP 503 errors and connection-pool exhaustion after deployment. INC-101 documented a configuration issue in which the maximum connection-pool size had been reduced. The search also returned the payment-service runbook and INC-103, an alternative historical incident where similar HTTP 503 symptoms were caused by a downstream dependency. This changed the investigation from identifying connection-pool exhaustion as the immediate symptom to a more specific hypothesis that the current deployment may include a connection-pool configuration change. Importantly, the agent recommended comparing current and previous connection-pool settings rather than claiming the historical cause was proven. This demonstrates the intended value of RAG: retrieved history can make the next investigation step more specific and grounded without being treated as proof.

Retrieval Design Choices
The retrieval design uses synthetic runbooks and historical incident reports because both contain reusable investigation knowledge while avoiding proprietary or sensitive enterprise data. Runbooks and historical incidents are organized as separate document categories within the synthetic knowledge directory. Embedding-based retrieval allows the system to locate documents by conceptual similarity rather than exact keyword overlap. The LLM generates queries from evidence accumulated during the current investigation. Because the current synthetic documents are small, each document can initially be treated as a retrieval unit; more advanced chunking can be added when the knowledge base contains longer documents. The implementation retrieves the top three semantically relevant results, allowing the agent to compare supporting and alternative explanations. Similarity scores and source information are returned so retrieval behavior remains observable during testing.

Retrieval Failure Mode and Risk Management
A major retrieval failure mode is retrieving a semantically similar but causally different incident. Semantic similarity does not guarantee that a retrieved document has the same root cause as the current incident. INC-103 illustrates this risk: it was relevant because it involved payment-service, HTTP 503 errors, and timeouts, but its historical root cause was a downstream dependency failure rather than database connection-pool exhaustion. If the agent blindly accepted the highest-ranked historical incident as the current root cause, retrieval could reduce reliability.
The design manages this risk by retrieving multiple results, combining retrieved knowledge with current incident details and operational logs, and requiring the agent to separate observed evidence from inferred hypotheses. Incomplete conclusions must be framed as hypotheses that require further verification, and historical causes must not be treated as facts about the current incident. In the current test, INC-101 provides a useful configuration hypothesis, while INC-103 shows that similar symptoms can have different causes.
